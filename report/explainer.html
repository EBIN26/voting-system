Our project explained

Secure blockchain-based voting system
By M. Ebin Virjo and K. Kirithika, ECE, VISTAS. This guide is for reading on your own, before the review or whenever you need it. No technical background in blockchain is assumed.

The whole project in one paragraph. A voter presses one button. Our server checks that the person is allowed to vote and has not voted yet, seals their vote inside an encrypted ballot that looks like random data, and writes that sealed ballot onto a public blockchain through a program called a smart contract. Nobody can open the ballots during the election. After it closes, two of three trustees combine their pieces of the secret key, open the ballots and count them. The key is then published, so anyone can open the ballots too and check that the count is honest.

1. The idea in everyday words

Imagine a glass ballot box in a public square, with a notebook next to it that everyone can read but nobody can erase.

  • Each voter puts in an envelope that is locked, so nobody can see the vote inside.
  • The notebook (the blockchain) records every envelope, in order, for ever. Nobody can remove or change an entry.
  • A rule book (the smart contract) stands guard: one envelope per voter, only during the voting hours, no more envelopes than voters.
  • The key to the envelopes is cut into three pieces and given to three trustees. Any two pieces together open the envelopes, but only after voting ends.
  • Afterwards the key is published, so anyone can open the envelopes and recount.

That is exactly what our system does, with computers instead of paper.

2. The problem we are solving

A good voting system has to do things that pull in opposite directions:

We needBut that is hard because
Only eligible people vote, and only onceWe must know who voted, yet…
Nobody can find out how someone voted…the record of who voted must not link to their choice.
Nobody can change the resultThe people running the system could be dishonest.
Anyone can check the resultYet the votes must stay secret until the end.

Our design splits the trust: the server knows who voted but not what they chose; the blockchain holds the sealed ballots but not the identities; the trustees can open the ballots but only together and only at the end.

4. What happens when you press Vote (the five steps)

Everything below runs automatically, in about a quarter of a second on our laptop (7 to 14 seconds on the real Sepolia network, because it waits for a real block).

Figure 2. The five backend steps. Each step can refuse the vote and stop.

Step 1. Check the request

Is the voter ID the right format? Is the candidate real? Does the blockchain say voting is open? If not, the vote is refused.

Step 2. Verify the voter (the “voter hash”)

We never store a real identity. We run the ID through a one-way scrambling function (HMAC-SHA-256, then Keccak-256) and get a long code, the voter hash. Scrambling is one-way: you can turn an ID into a hash, but not a hash back into an ID. The electoral roll holds only these hashes. If the voter's hash is on the roll, they are allowed to vote.

Step 3. Issue a one-time token

We make a random 32-byte token and store only its hash. The token table has no voter column and no time stamp, so even someone who reads the whole database cannot tell which token belongs to which voter. The voter is marked “already voted”, so pressing Vote again is refused here.

Step 4. Encrypt the ballot

The ballot (candidate number plus 16 random bytes) is locked in two layers. AES-256-GCM locks the vote fast and also notices any tampering. Then the AES key itself is locked with the election's RSA-3072 public key. Think of it as a fast padlock for the vote and a very strong lockbox for that padlock's key. The result is always exactly 430 bytes, whoever you vote for, so the size gives nothing away. The 16 random bytes make two votes for the same candidate look completely different.

Figure 3. Inside the 430-byte ballot.

Step 5. Record on the blockchain

The server sends the sealed ballot and the token's hash to the smart contract. The contract checks its own rules: right time window, token not used before, ballot not too big, not more ballots than voters. If everything is fine, it stores the ballot permanently and the voter gets a receipt (transaction hash and block number). If a rule fails, the contract refuses and the server releases the token so the voter can try again.

Honest note about the demo page. In this one-button page the server does the encryption, so it briefly sees who voted for whom. Our full voter app encrypts in the voter's own browser instead. We chose the simpler version for the demonstration, and the report says so clearly.

5. The election from start to finish

Figure 4. The four phases. They only move forward.

PhaseWhat happens
SetupThe key ceremony makes the election key and splits the private part into three trustee pieces (Shamir secret sharing: any 2 of 3 rebuild it, 1 piece alone is useless). The contract is deployed with the candidates, the trustees and the key's hash.
VotingThe administrator opens the election with a time window (for example 5 minutes). Voters press Vote. The contract accepts ballots only inside the window.
ClosedAfter the end time anyone can close the election. Nobody, not even the administrator, can close it early. Two trustees rebuild the key, decrypt the ballots and count. Ballots that cannot be decrypted count as invalid and never stop the count.
FinalizedEach of the two trustees submits the count from their own wallet. When two identical counts arrive, the contract locks in the result. The key is published, and anyone can run the recount tool to check.

6. The cloud part

To show the system working like a real website, the backend runs on a free Oracle Cloud server and the contract is on the Sepolia public test blockchain. Sepolia uses fake money (test ether), so nothing costs anything.

PieceWhat it is for
Oracle Cloud VMA small Linux computer (Ubuntu 24.04, 1 GB memory) that is always on and has a public address.
DockerPacks our backend and everything it needs into one container, so it runs the same everywhere.
CaddySits in front of the backend and gets a free HTTPS certificate automatically (the padlock in the browser).
DuckDNSA free name (e-voting-system.duckdns.org) that points to the server's address.
SepoliaA public Ethereum test network. Anyone can look up our contract on Etherscan.
EtherscanA website that shows every transaction on the blockchain, which proves the election really ran there.

What stays OFF the server: the administrator's wallet key, the trustees' key pieces and the private election key. The server holds only the public key and its own “submitter” key (which can only submit ballots). So even a stolen server cannot read votes or change the rules.

8. What is NOT done (be honest about this)

  • The demo uses dummy voter IDs. There is no real identity check (such as an OTP) in the demo.
  • In the demo page the server encrypts the ballot, so it sees the voter and the choice together.
  • One backend submits all ballots. It cannot read or change them, but it could refuse to submit.
  • The trustee passphrases are public in the demo, so the key pieces protect nothing in this run.
  • The higher gas on Sepolia is unexplained.
  • No independent security audit. It is a prototype, not ready for a real election.

10. How to run it yourself

Quick local demo (no cloud, no internet needed)

Open PowerShell and go to the project folder, then run one command. It starts a local test blockchain, makes the key, deploys the contract, opens the election and starts the voting page:

cd D:\claude\test-voting\gov-evoting-live

npm run demo:simple

Open the address it prints in your browser and press a Vote button. Stop it with Ctrl+C. (If it says a port is busy, an earlier demo is still running. Close it first.)

The live cloud version

Open https://e-voting-system.duckdns.org/simple.html. The election has to be opened from Ebin's computer first with node scripts/admin.js --live open 4 60 300, which needs the wallet files that stay on that computer. The cue card has the full sequence.


11. Glossary: words you will hear

TermPlain meaning
BlockchainA shared record kept by many computers. New entries are added, never removed or edited.
Smart contractA program stored on the blockchain that runs exactly as written. Ours enforces the election rules.
Ethereum / SepoliaA blockchain that supports smart contracts / its free public test version.
WalletAn account on the blockchain, controlled by a secret key.
GasThe fee unit for running things on the blockchain. More work or storage means more gas.
Transaction / blockOne action written to the chain / a batch of transactions added together.
HashA one-way scramble that turns any data into a fixed-size code. You cannot reverse it.
Keccak-256The hash function Ethereum uses (the original design behind SHA-3).
HMACA hash mixed with a secret, so nobody can guess inputs by trying them all.
AES-256-GCMFast encryption that also detects any change to the data.
RSA-OAEPPublic-key encryption: anyone can lock with the public key, only the private key unlocks.
Hybrid encryptionUsing AES for the data and RSA to protect the AES key. Fast and strong.
Shamir secret sharingSplitting a secret into pieces so that a minimum number (here 2 of 3) rebuild it.
TrusteeA person who holds one piece of the key.
TokenA random one-time code that lets one voter cast one ballot.
Electoral rollThe list of who may vote (ours holds only hashes).
Docker / CaddySoftware that packs our server for the cloud / adds HTTPS in front of it.

12. Questions you should be able to answer

  1. Why a blockchain? So nobody alone can change the rules or the ballots, and the public can check them.
  2. How is the vote secret on a public chain? Only encrypted 430-byte ballots go on it.
  3. How is double voting stopped? One token per voter, checked in the database and again by the contract.
  4. Who can open the ballots? Any two of three trustees together, only after the election closes.
  5. Can the administrator cheat? No. They only open the election, and cannot read, change or close early.
  6. What if the cloud server is hacked? It holds only the public key, so votes stay sealed and the rules stay fixed.
  7. What is simulated? The voter IDs are dummy. Real identity checking is future work.
  8. Why is Sepolia slower than local? It waits for a real block (7 to 14 s).
  9. Why is the gas different? We measured both and have not found the cause yet.
  10. Is it ready for a real election? No. It is a prototype with no audit.
